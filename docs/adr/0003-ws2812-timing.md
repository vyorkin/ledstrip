# Тайминг WS2812 на STM32: CCR 38/75

## Контекст

Тикет #1 зафиксировал для STM32 `CCR3 = 50` для нуля и `100` для
единицы. Это даёт T0H/T0L = 0.5/0.75 мкс и T1H/T1L = 1.0/0.25 мкс.
Контракт `docs/interface.md` и AVR-эталон используют другие значения:
T0H/T1H 0.375/0.75 мкс, T0L/T1L 0.875/0.5 мкс (16 МГц, 20 тактов на
бит: 6/12 тактов высокого уровня). При 50/100 T1L = 0.25 мкс лежит на
нижней границе допустимого для WS2812B и может читаться как ложный
старт следующего бита.

## Решение

STM32 выдаёт биты с `CCR3 = 38` для нуля и `75` для единицы при периоде
125 тиков по 10 нс:

| Параметр | Значение | Контракт |
|---|---|---|
| T0H | 0.38 мкс (38 тиков) | 0.375 мкс |
| T1H | 0.75 мкс (75 тиков) | 0.75 мкс |
| T0L | 0.87 мкс (87 тиков) | 0.875 мкс |
| T1L | 0.50 мкс (50 тиков) | 0.5 мкс |

T0H — единственное округление: 37.5 тика нельзя записать в CCR.
Период остаётся 1.25 мкс (800 кГц), буфер — 2880 полуслов.

Это отменяет пункт «CCR 50/100» в Implementation Decisions тикета #1.
Остальные решения #1 по WS2812 (PB0, TIM3_CH3, 800 кГц, 2880 полуслов,
DMA, низкий уровень ≥50 мкс, без bit-banging) не меняются.

## Последствия

- STM32 и AVR выдают одинаковый тайминг; цвета не должны сдвигаться при
  переходе на новую платформу.
- Host-тест `test_ws2812()` проверяет период и все четыре времени по
  контракту, поэтому случайное изменение CCR ломает сборку тестов.
- Bench-ожидания в `docs/bench-results.md` и `docs/bench-remote.md`
  обновлены на 0.38/0.87/0.75/0.50 мкс.

## Отвергнутые альтернативы

- **Оставить 50/100 из #1** — короче T1L 0.25 мкс, риск ложного бита на
  WS2812B и расхождение с AVR-эталоном.
- **CCR 40/80** — ровные 0.4/0.8 мкс, но T0H дальше от контракта 0.375,
  чем 38, и T1H не совпадает с AVR 0.75.
- **Изменить частоту таймера** — 100 МГц уже даёт 10 нс на тик; другая
  частота усложняет PLL и не улучшает округление T0H.
